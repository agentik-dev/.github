Guardrails for long, unattended Claude Code work.

agentik is five Claude Code plugins, with command line tools, for agent work that runs for hours with nobody watching. Each plugin installs and works alone, and one command, agentik, installs and checks them.

agentik is alpha. It is built and used on macOS by one owner, expect breaking changes between versions, and it is not affiliated with Anthropic.

Overview

Long Claude Code work goes wrong in five ways

When Claude Code runs for hours, a few problems keep coming back. A session fills up, runs out of room to hand off, stops when nobody is there, forgets what you decided, or reports a success it did not reach. agentik is a set of tools that each answer one of these.

What goes wrong without these tools

A session fills up and summarises itself

You come back to a session that has compressed its own history, and the exact file names and numbers it held are gone.

A session runs out of room to hand off

A session that runs to 100% of its window has no room left to write down what it was doing, commit its work, or pass it on. You find it stopped mid-task with nothing recorded.

Work stops when nobody is there

On one day in one owner's use, a session reached its stopping point three times and each time sat idle until a person restarted it: 113, 181 and 83 minutes, 6 hours 17 minutes in all.

What you decided is lost or decided twice

A session repeats a choice you rejected last week, because the rejection sits in a long log it never opened. The log has grown past what any session can read, and its index has fallen behind.

A report says success when it was not

One coordinating session ended its run while four helpers were still working, which stopped them. The result read as success, and four branches held unfinished changes.

What you get

A session stops before it fills up and leaves a note

A session ends at a point chosen for efficiency, not when it runs out of room. Its budget sits below the model's window, around where a long context is well understood to start doing worse and costing more each turn. A meter reads after every tool call, and at 80% of that budget the session writes a short handoff note, called the charter, and commits.

Long work goes on without automatic compaction

A launcher restarts the session from its charter. Claude Code's automatic compaction is blocked; a /compact you type yourself still runs.

What you decided reaches every session

One decision file holds at most 25 entries in force. The few rules every session needs are copied into CLAUDE.md, which every session loads.

Unattended work merges only when its checks pass

Each task gets its own branch and its own session. A task whose checks fail waits, with a claude --resume line that reopens its session.

Setup

One command installs the default plugins

One clone and one setup put three plugins into Claude Code and the agentik command on your terminal. Setup shows its plan and asks once before it writes anything.

Setup installs session, decisions and agents. respeak and relay are added by name, with agentik setup respeak and agentik setup relay.

What setup does

  1. Run the two lines under "Commands". Setup shows a seven-step plan and asks one question. Off a terminal it needs --yes.
  2. On yes, setup installs one step at a time and stops at the first failure.
  3. If ~/.local/bin is not on your PATH, setup prints the export PATH line. It edits no shell profile, so you add the line yourself.
  4. Start claude.

This screen is an example. The names in it, such as acme-cli and lamp, are example values.

                no sitting is live

Commands and what you need

git clone https://github.com/agentik-dev/agentik-commons && agentik-commons/setup
claude
agentik doctor
agentik status
agentik remove --all --dry-run

agentik doctor reads the machine and gives a mending line for each failure. agentik remove --all --dry-run shows what leaving would remove; run it without --dry-run to leave. Config and state stay.

You need Claude Code, git and the system's Python 3.9 or newer. Setup installs no package. To type agentik afterwards, ~/.local/bin must be on your PATH. The tools are built and used on macOS; they are not tested elsewhere.

Session

Give each session a budget, a note and a fresh start

A long task can fill the session that runs it, and Claude Code then summarises the session into a shorter one. The session plugin gives each session a budget it can see and a checkpoint at 80% of it. At the checkpoint the session writes a short handoff note, called the charter, and a launcher starts a fresh session that reads it.

You come back to a session that has compacted itself, and the exact file names and numbers it held are gone. A session that runs to 100% has no room left to write down where it was, and a restart by hand waits until a person is there.

The budget has a ceiling for context (how much the session holds) and one for turns, both set below the model's window. The numbers are choices: 180,000 tokens and 400 turns for most sessions, 400,000 tokens on a 1M window for orchestrators, and a checkpoint at 80%. The charter is one file, under 4,096 bytes, that says what the session is for, what is done and what comes next. The ceiling and the checkpoint tell the session what to do and stop nothing. Claude Code's automatic compaction is blocked; a /compact you type yourself still runs.

How it runs

  1. You start the session with agentik session run. After every tool call a meter reads its budget, and two lines above your prompt, the band, show you where it stands. The band tells and advises; it stops nothing.
  2. At 80% of a ceiling the session is told to bring its charter current, commit, and end its turn.
  3. The launcher restarts it only within its guards. You can end the loop by leaving a STOP file, and it restarts at most 20 times in 24 hours.
  4. The launcher starts a fresh session with the same arguments, and the new session reads the charter's Next act.

What you see

The names and figures in these screens are example values.

The band, first line, in the clear zone
session: opus 5.5 · 1M · ctx 46% · turns 13%
The checkpoint line the model is shown at 80%

The check queue

Ten helpers (subagents a session starts) that each run the full tests at once can swamp a machine. The check queue lets one run go at a time for each repository, under a load limit, and cuts each run at a time limit.

Commands and what you need

agentik session run
agentik session status
/session:status
/session:checkpoint

The session plugin needs Claude Code and the system's Python 3.9 or newer. It needs no clone and no package. Setup installs it.

Decisions

What you settled, in one short file every session reads

A project keeps what it has settled in one short file, DECISIONS.md. The decisions plugin copies the few rules every session must follow into CLAUDE.md, which every session loads, and agents put their questions to you in one batch.

The first user of the decisions tool kept a log of 214 rulings. It had grown past what any session could read whole, and its hand-kept index had fallen behind, so a session could repeat a choice that was already rejected.

A project has one decision file with at most 25 entries in force; the cap is a choice. Questions come with two to four options, the first one recommended, and at most five are open at a time. An entry goes into force through answer, which records your answer and where it came from. The tool cannot tell who typed the answer.

How a question becomes a rule

  1. An agent meets a fork and runs new, which writes a question into OPEN-QUESTIONS.md.
  2. ask puts the open questions to you in one batch. If respeak is installed, it renders them once first.
  3. You answer, and answer records the entry in force in DECISIONS.md.
  4. render writes the generated block into CLAUDE.md. Every session loads the block on every turn and reads any entry in full with show N.

Agents

See every session and helper in one table

Three terminals are open and a dozen helpers are running, and you cannot tell which one is stuck. A helper is a subagent that a session starts. The agents plugin builds one table of what each session and helper is doing right now. Optionally, a session's routine side work can run on a local model, while the session itself stays on your Claude subscription.

The table

agentik agents status is read-only. It shows a row for each session, helper and local agent, with these columns in order: id, lane, model, elapsed, turns, context, cost, last tool, state, what. A lane is the route a request takes to a model. The rows come from the session plugin, and with no session plugin records the table says so.

the table's column header
id  lane  model  elapsed  turns  context  cost  last tool  state  what
the empty table's second line
no agents in the last 30 min

The local lane

A local lane sends a session's routine side work to a model on your own machine, at no marginal cost. It needs Ollama 0.33.0 or later and a model of about 30 GB. While a session is pointed at the local lane, Claude Code's Remote Control does not work in it.

How the local lane works

  1. agentik agents local runs a check first and refuses to start when it fails.
  2. It starts a router on your machine and points Claude Code at it. Requests go by model name: local/* to the local server, and sonnet, opus and fable to Claude.
  3. A ledger records tokens, wall time and agent ids, and never a prompt.

The scribe

agents:scribe runs on Sonnet. It takes a builder's or reviewer's hand-back and writes it into the repo's records. It never merges or pushes.

Commands and what you need

/agents:status
ollama pull qwen3.8:27b-mtp-q8_0
agentik agents route --check
agentik agents local

The table needs Claude Code, bash and the system's Python 3.9 or newer, and works alone. Setup installs agents. The local lane is optional. agentik agents route --check names whatever is missing, and the model is about 30 GB.

Relay

Write tasks down, start a run, read one report

You write several tasks down, start a run and walk away. Each task gets its own branch and its own Claude Code session, and merges into main only when its checks pass. When the run ends you read one report, and every stopped task keeps a line that reopens its session.

Nobody is there to catch what goes wrong. A session can start more sessions, a crash can leave a lock held, and every task costs money. So a run has two money caps, a clock and a circuit breaker.

A run pushes nothing, and neither do the sessions it starts.

How a run goes

  1. Write each task as a task file, listed in relay/queue.yaml in your repo. plan checks the queue and the files and starts nothing.
  2. run gives each task its own working copy of the repo (a git worktree) and a branch, and starts one headless Claude Code session on it. The session commits each step.
  3. A task whose checks are green merges into main. A red task is parked with its reason and a resume line, agentik relay resume <row>, where <row> is the task's id. The run goes on to the next task. A run ends at an empty queue, the task count, the clock, a stop from you or a failure, and a usage limit pauses it until the limit resets.
  4. agentik relay report shows the merged commits, each stop word for word, the cost of each session, the branches waiting and the resume lines.

Both money caps overshoot. A session can pass its budget by one response plus its running helpers, and --max-usd never stops a running session.

Commands and what you need

relay has two parts, a plugin and a program. The first line below adds the plugin and builds the program into ~/.local/bin. Setup does not install relay by default.

claude plugin marketplace add agentik-dev/agentik-commons; claude plugin install relay@agentik; GOBIN="$HOME/.local/bin" go install github.com/agentik-dev/agentik-relay/cmd/agentik-relay@latest
agentik relay plan --rows ar1,ar2 --until 18:00
agentik relay run --until 18:00 --max-sittings 4 --max-usd 20 --parallel 2
agentik relay report

relay needs Go 1.26 or newer, git and Claude Code. tmux is optional. The plugin's slash commands need ~/.local/bin on your PATH. A go install without GOBIN writes to Go's own folder, which is on no one's PATH.

Respeak

Reports written for the person who reads them

A report can be correct and unreadable. respeak rewrites an agent's report for the person who has to read it: a newcomer, a manager or a peer. Nothing runs until you call it.

A 300-line build log is right, and your manager needs the three lines that matter first. respeak starts from a premise of its design: agents drift into shorthand when they write for each other.

Three modes

ModeForHow it reads
eli5A newcomerOne idea per sentence, at most one analogy, and the next sentence says the real thing.
blufA managerThe result, decision or ask first, with its owner and deadline. You can forward it unedited.
technicalA peerThe conclusion first, then evidence as file and line or a command, then open questions.

How it works

  1. You run /respeak:respeak [mode] [source].
  2. The skill reads the source and sets the tone for that file from layers: plugin defaults, your file, the project's, a folder's .respeak.yaml, the session's, and this call.
  3. The translator agent works in its own context window, on Sonnet, and the scanner checks banned phrases, em-dash density and sentence length.
  4. The narrative comes back to you.

What it will not change

Error messages, security findings, quotes and numbers with units are never compressed. A claim that work is done, fixed, passing or green is stated as fact only when the source holds the tool result that shows it. Otherwise it reads: claimed, not verified.

A confident summary that is wrong is worse than the raw report. The scanner step can be denied, and then the render goes unmeasured. The style check is opt-in per project.

Commands and what you need

claude plugin marketplace add agentik-dev/agentik-commons; claude plugin install respeak@agentik
/respeak:respeak bluf README.md
claude plugin install respeak@agentik --config default_mode=bluf

respeak needs Claude Code 2.1.196 or newer, a plugin path without spaces, bash 3.2 or newer, and a python3 (3.9 or newer) with PyYAML. Setup does not install it by default; agentik setup respeak adds it.

Context

How a session stays inside its budget

Each session stops well short of its window, writes a note, and a fresh session carries on from it. Below: the rule, why the budget sits below the window, what you see on screen, and what one owner's record shows. A session here is what the primers call a sitting.

The rule in five lines

  1. Each session gets a ceiling set below the model's window.
  2. A meter reads after every tool call.
  3. At 80% of a ceiling the session writes its charter and commits.
  4. The launcher restarts the session.
  5. The new session reads the charter's Next act and carries on.

Why a ceiling below the window

Three reasons rest on outside evidence: a long context does worse, a summary drops specifics, and every turn pays for the whole context. One is the makers': a session needs room to write its handoff. The numbers, 180,000 and 400,000 tokens, 400 turns and the 80% checkpoint, are choices, not measurements.

What you see

The band is the two lines above Claude Code's prompt. They are for you. The model reads separate lines that the hooks add; the checkpoint line on the session tab is one of them.

How the restart works

What the record shows

Advanced

Nine design choices, and what each turned down

This tab is for backend and systems engineers. Each block states a choice, the alternative it turned down, why, and a link to the research page that backs it. Numbers marked rulings are the makers' choices, not measurements. The research site is a collection of detailed documents, and its pages carry evidence levels.

1. A ceiling set below the context window

The choice. Each role gets 180,000 tokens and 400 turns, orchestrators get 400,000 tokens on a 1M window, and the checkpoint is at 80%.

Turned down. Running to the model's window. A long context does worse, each turn pays for the whole context, and a full session has no room to hand off. The numbers are rulings.

2. Restart, never compact

The choice. Block Claude Code's automatic compaction (trigger auto) and restart from a written charter. A typed /compact, and any trigger the hook does not know, pass.

Turned down. Compaction. A summary keeps the gist and loses exact values, and a compaction needs a person's hand. No controlled study compares the two.

  • Question 2: compaction or restart

3. The charter as the one thing carried across a restart

The choice. One file per session, six parts, under 4,096 bytes. The launcher reads only its ## Next act.

Turned down. Carrying the old context, or a long state file read whole.

4. The usage band and admission

The choice. Keep every five-hour and seven-day usage reading in one ledger for the machine, fit a burn rate for each model family, project the window's peak at its reset, and tell the session room for N under a ceiling of 97 less a margin of 3. Today it advises only.

Turned down, for now. Refusing or deferring spawns. That is designed, not built. Metering the session's own usage is marked "our use and a conjecture" in the research summary.

  • Living inside a usage window
  • Budgets and pacing, question 4

5. The gate queue that holds every build and test

The choice. Every make check goes through one queue for each state root, one running for each repo (keyed on the repo's git common directory, so worktrees count as the repo), under a load ceiling and cut at a time limit. The tool reports exit codes and judges none.

Turned down. Each session running its own checks at once. A design review counted 310 concurrent check runs, 620 node starts and 310 test suites, with no timeout, lock or load check.

  • The problem

6. The decisions ledger, and the block rendered from it

The choice. One sectioned DECISIONS.md for each repo, at most 25 in force, and a generated block in CLAUDE.md holding the Every session entries word for word and one line for each other entry. The cap is the owner's ruling; no outside source gives 25.

Turned down. A long log read by hand, with a hand-kept index. The index fell behind.

7. Landing as one job

The choice. One call takes a reviewed branch to landed: check, hygiene scan, merge --no-ff onto main, remove the worktree, delete the branch, all in one gate job. Only if asked does it then publish (prove main's head green, scan, push that sha) and install.

Turned down. Landing by hand in several steps that a restart could cut in two. Every stage is read from git, so a second call after a restart goes on.

9. The unattended loop

The choice. agentik session unattended run <repo> runs the rows of relay/queue.yaml in order, one claude -p builder each in its own worktree, lands each green row as one gate job, never pushes, and stops at the queue's end, a clock, a count, a limit, an auth error or a stop file.

Turned down for the loop. Parallel rows, the relay's circuit breaker, and a push after the run. The loop runs beside the Go relay through 2026-12-31, on a stated bar: at least twelve runs and thirty rows, twenty landed, no hand fix after a merge, and no harm. The relay's gate rule is that an unknown result is never a pass.
